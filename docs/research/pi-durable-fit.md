# Research: Pi Durable as the basis for afk-kit

- **Date:** 2026-10-11
- **Ticket:** [#92](https://github.com/juranki/afk-kit/issues/92)
- **Question:** Does Pi Durable 1.1.0 provide a better foundation for afk-kit's unattended delivery workflow?
- **Method:** first-party announcement, release-tag documentation, normative specification, and source inspection against afk-kit's current contracts. No implementation, benchmark, live model run, or migration was performed.
- **Upstream baseline:** [`v1.1.0`](https://github.com/earendil-works/pi/releases/tag/v1.1.0), commit `abe508e1b89912adde45528136c3221eb69acdd7`. Both [`pi-coding-agent`](https://github.com/earendil-works/pi/blob/abe508e1b89912adde45528136c3221eb69acdd7/packages/coding-agent/package.json) and [`pi-durable`](https://github.com/earendil-works/pi/blob/abe508e1b89912adde45528136c3221eb69acdd7/packages/durable/package.json) are version 1.1.0. Durable's changelog dates that release 2026-10-07.

## Recommendation

**Pi Durable is a strong candidate for the agent execution substrate, and a possible later foundation for Engine task persistence. It is not a drop-in replacement for the Coordinator or a reason to replace the existing deterministic workflow with an agent-directed one.** Evaluate it behind an adapter before adopting it.

Its useful overlap is the machinery afk-kit currently builds around individual sessions: durable transcripts, streamed evidence, explicit task ownership, cancellation, per-role configuration, atomic application state, and restart inspection. The difficult parts remain afk-kit's domain policy and trust boundaries: Readiness before Claim, an immutable Agent brief, bounded fresh Implementer sessions, independent Verify commands and Reviews, confinement, tracker/Git reconciliation, Escalation, and the human Merge gate. Those are not supplied by a general agent harness. Compare the [ontology](../../system-intent/ontologies/agent-delivery-workflow.md), [current Coordinator playbook](../playbooks/coordinator-session.md), and [Engine ports](../../engine/ports.ts) with the [release specification](https://github.com/earendil-works/pi/blob/abe508e1b89912adde45528136c3221eb69acdd7/packages/durable/docs/spec.md).

The largest conflict is deliberate: afk-kit v0 finalizes a hard interruption through Escalation and **never resumes it automatically**. Pi Durable is designed to resume pending work. Adopting that default would change delivery policy, not merely improve storage. The current rule is explicit in [the confirmed v0 specification](https://github.com/juranki/afk-kit/issues/46#issuecomment-5849489182) and [the crash reconciler](../../engine/runs/reconcile.ts); Durable's contrasting behavior is in its [recovery specification, sections 5.2–5.4](https://github.com/earendil-works/pi/blob/abe508e1b89912adde45528136c3221eb69acdd7/packages/durable/docs/spec.md#52-execution).

## Release and maturity

The [announcement](https://earendil.com/posts/pi-durable/) introduced Durable alongside Pi 1.0 on October 1. It calls Durable a separate framework for agent applications, rather than a replacement for the coding agent. Both are now released at 1.1.0, but the [Durable README](https://github.com/earendil-works/pi/blob/abe508e1b89912adde45528136c3221eb69acdd7/packages/durable/README.md) still explicitly calls its API experimental and subject to unannounced changes between releases. Pi coding agent stability does not establish Durable API stability.

The user-linked `main` README is ahead of this release. At the inspected main commit `96abe9a5ad45005cae34ed1c52d42f71fc88bedc`, the [unreleased changelog](https://github.com/earendil-works/pi/blob/96abe9a5ad45005cae34ed1c52d42f71fc88bedc/packages/durable/CHANGELOG.md) includes `content` becoming `output`, nested tool execution, structured tool outputs, and `abandonOnRestart`. These are **not 1.1.0 capabilities**. A spike must use release-tag examples and exact dependency resolution, not current-main snippets. Already the [1.1.0 changelog](https://github.com/earendil-works/pi/blob/abe508e1b89912adde45528136c3221eb69acdd7/packages/durable/CHANGELOG.md) changes storage query and task context interfaces.

Durable is MIT licensed, declares Node `>=22.19.0`, and directly depends on `pi-ai` and Chord, not the coding-agent SDK. afk-kit currently executes through Bun and develops against coding-agent 0.85.1. Portable storage interfaces make a Bun adapter possible; they do not prove the shipped Node SQLite adapter works under afk-kit's host. These are separate upgrade and runtime-compatibility questions. Sources: [upstream package](https://github.com/earendil-works/pi/blob/abe508e1b89912adde45528136c3221eb69acdd7/packages/durable/package.json), [Node adapter](https://github.com/earendil-works/pi/blob/abe508e1b89912adde45528136c3221eb69acdd7/packages/durable/src/storage/sqlite/node.ts), [local manifest](../../package.json).

## Fit against the workflow

| afk-kit requirement | What Durable contributes | What afk-kit must retain or build |
| --- | --- | --- |
| Deterministic Coordinator | Versioned custom task phases and atomic checkpoints | The existing state machine, ordered operations, explicit start, and terminal outcomes |
| Separate Readiness check | Per-conversation model, instructions, tools, and environment | Read-only evidence tools, 15-minute bound, output validation, no Verify execution, and no Claim on assessment failure |
| Immutable prepared handoff | Immutable transcript entries and typed documents committed together | Source capture, provenance/hash, binding-versus-guidance distinction, and identical Implementer/Spec Reviewer input |
| Fresh Implementer and Reviewer contexts | Separately created conversations with explicit role configuration | New conversations each cycle; do not reuse or fork an Implementer context into a Reviewer |
| Independent Verify and Reviews | Custom tasks, child waits, ownership | Verify executed by Engine, not accepted from model claims; Standards and Spec Reviews both approve |
| Confined local commits | Replaceable `ExecutionEnv` used by file/process tools | The existing OS/network boundary, credential isolation, independent clone, and separate trusted publishing path |
| Caps and failure visibility | Usage ledger, retry state, task inspection, cancellation | Persisted deadlines/cycle counter, explicit stop conditions, Escalation and tracker comment |
| Inspectable progress | Committed transcript/output, watches, experimental agent event stream | Stable public `events.jsonl` and `afk status` contract, artifact locations, and useful diagnostics |
| Claim/Git/tracker safety | Atomic internal commits and replay-aware tool execution | External locks, live safeguards, idempotency keys/world reconciliation, compensation, and maintainer-only merge |

Upstream evidence: [task specification](https://github.com/earendil-works/pi/blob/abe508e1b89912adde45528136c3221eb69acdd7/packages/durable/docs/spec.md#5-durable-tasks), [role configuration and environment API](https://github.com/earendil-works/pi/blob/abe508e1b89912adde45528136c3221eb69acdd7/packages/durable/src/harness/types.ts), [foreground Subagent example](https://github.com/earendil-works/pi/blob/abe508e1b89912adde45528136c3221eb69acdd7/packages/durable/test/examples/22-subagent-foreground.ts), and [usage implementation](https://github.com/earendil-works/pi/blob/abe508e1b89912adde45528136c3221eb69acdd7/packages/durable/src/harness/usage.ts). Local requirements: [ADR 0016](../adr/0016-agentic-readiness-and-prepared-brief.md), [agent factories](../../engine/agent-runner.ts), [confinement](../../engine/confinement.ts), and [v0 specification](https://github.com/juranki/afk-kit/issues/46#issuecomment-5849489182).

## Recovery is useful, but not external exactly-once execution

Durable commits a tool's execution intent before calling it. On recovery, a tool reruns only if both its stored and current replay policies are `safe`; otherwise the harness writes an interrupted error result carrying the committed partial output. Built-in bash does not declare replay safety. The model can continue after that result, so making bash unsafe does **not** implement afk-kit's whole-Run no-resume rule. Sources: [ToolTask implementation](https://github.com/earendil-works/pi/blob/abe508e1b89912adde45528136c3221eb69acdd7/packages/durable/src/harness/tool.ts) and [bash implementation](https://github.com/earendil-works/pi/blob/abe508e1b89912adde45528136c3221eb69acdd7/packages/durable/src/tools/bash.ts).

An atomic transcript/document/task transaction cannot include a Git push, GitHub assignment, PR mutation, shell write, or provider charge. A crash after an external effect but before the result commit leaves uncertainty. `replay: "safe"` is an application promise, not a harness guarantee. The [child-task example](https://github.com/earendil-works/pi/blob/abe508e1b89912adde45528136c3221eb69acdd7/packages/durable/test/examples/24-child-tasks.ts) makes payment idempotency the application's responsibility. The existing [side-effect intent journal and reconciler](../../engine/runs/reconcile.ts) remain valuable for the analogous GitHub/Git cases.

Abort ownership is a good match for a Coordinator owning Implementer and Review work. However, cancellation of a caller's wait cancels only the wait, and background tasks survive ordinary conversation abort. Closing the harness stops invocations without recording cancellation, leaving work resumable. Deadline handling must issue durable aborts for all owned work and enforce subprocess termination; it must not merely stop awaiting a promise or close storage. Sources: [ownership/abort specification, section 5.4](https://github.com/earendil-works/pi/blob/abe508e1b89912adde45528136c3221eb69acdd7/packages/durable/docs/spec.md#54-scheduler-abort-and-ownership) and [background Subagent example](https://github.com/earendil-works/pi/blob/abe508e1b89912adde45528136c3221eb69acdd7/packages/durable/test/examples/23-subagent-background.ts).

## Remaining operational obligations

**Storage ownership.** One process owns a Durable store; upstream supplies no cross-process ownership lock. SQLite's busy timeout is not a scheduler/Claim lease. Per-Run stores fit per-issue processes better than a shared database, but afk-kit still needs same-Issue exclusion and a read-only status path that never starts pending work. `submit`, `wait`, and explicit `resume` start scheduling; observation should stay on inspection APIs. Sources: [storage and Harness specification](https://github.com/earendil-works/pi/blob/abe508e1b89912adde45528136c3221eb69acdd7/packages/durable/docs/spec.md) and [Run lock implementation](../../engine/runs/store.ts).

**Durability level.** The Node SQLite adapter uses WAL and `synchronous=NORMAL`; ordinary process crashes preserve commits, but newest commits can disappear after power/host failure. JSONL defaults to no fsync; enabling fsync strengthens it, while its [implementation keeps a MemoryStorage copy](https://github.com/earendil-works/pi/blob/abe508e1b89912adde45528136c3221eb69acdd7/packages/durable/src/storage/jsonl/storage.ts), so retained history also consumes memory. The existing [Engine event append fsyncs each event](../../engine/runs/events.ts). Replacing it with a weaker default would need an explicit durability decision, and even stronger storage does not eliminate external-effect reconciliation. Sources: [SQLite adapter](https://github.com/earendil-works/pi/blob/abe508e1b89912adde45528136c3221eb69acdd7/packages/durable/src/storage/sqlite/node.ts) and [storage specification](https://github.com/earendil-works/pi/blob/abe508e1b89912adde45528136c3221eb69acdd7/packages/durable/docs/spec.md#10-storage).

**Confinement.** `cwd` chooses a directory; it does not create a security boundary. NodeExecutionEnv accepts absolute paths and expands home-relative paths. The upstream “sandbox per conversation” example explicitly uses a directory and says a hosted application should supply a container environment. The Implementer must also be unable to alter the Durable database, Run journal, or captured handoff. All enabled file and process tools must cross afk-kit's actual sandbox boundary; wrapping only bash while enabling host-side write/edit would weaken it. Sources: [Node environment](https://github.com/earendil-works/pi/blob/abe508e1b89912adde45528136c3221eb69acdd7/packages/durable/src/env/node.ts), [sandbox example](https://github.com/earendil-works/pi/blob/abe508e1b89912adde45528136c3221eb69acdd7/packages/durable/test/examples/29-sandbox-per-conversation.ts), and [ADR 0014](../adr/0014-ticket-worktree-is-an-independent-clone.md).

**Bounded spending.** Durable accounts reported model/tool usage, including compaction and failed attempts; this helps explain costs. It supplies no afk-kit cycle policy or global financial ceiling. Model retries, tool timeouts, compaction, child tasks, and the overall Run deadline must share afk-kit's limits. Unreported provider work after a crash can still have been billed. Sources: [usage accounting](https://github.com/earendil-works/pi/blob/abe508e1b89912adde45528136c3221eb69acdd7/packages/durable/src/harness/usage.ts), [generation/retry code](https://github.com/earendil-works/pi/blob/abe508e1b89912adde45528136c3221eb69acdd7/packages/durable/src/harness/generation.ts), and [Engine clock seam](../../engine/drive-clock.ts).

**Reproducibility and migration.** Agent choices persist by name, but registry code and settings do not persist. Reopening after an extension/model/configuration upgrade can execute different code. Tasks support versions/migrations and inspection of missing/old definitions, but afk-kit must pin and validate the code and configuration permitted to run. Retain the exact installed skill text/hashes required by [ADR 0015](../adr/0015-unattended-implementation-runs-the-installed-implementation-skills.md); Durable is not a drop-in implementation of the coding agent's ResourceLoader/skill mounting. Sources: [registry](https://github.com/earendil-works/pi/blob/abe508e1b89912adde45528136c3221eb69acdd7/packages/durable/src/harness/registry.ts), [task version specification](https://github.com/earendil-works/pi/blob/abe508e1b89912adde45528136c3221eb69acdd7/packages/durable/docs/spec.md#54-scheduler-abort-and-ownership), and [local configuration pins](../../engine/config.ts).

## An incremental evaluation

First test a **SessionFactory adapter**: keep the pure [Engine machine](../../engine/machine.ts), [driver](../../engine/drive.ts), existing journal, trusted tracker/Git operations, and policy. Replace one role session at a time with a fresh Durable conversation, explicit tools/instructions/model and confined environment. Keep Durable transcript storage subordinate to the Engine's authoritative Run journal. A killed process must be inspected and finalized through existing Escalation without scheduling old agent work; v1.1.0 has no released `abandonOnRestart` shortcut.

Only after this proves useful, evaluate moving linear Engine phase execution and persistence into custom tasks. Durable can run a simple workflow; its task graph capability does not require afk-kit to expose a general task graph or broaden v0 scope. Choose one authoritative Run history and a defined projection/export contract. Two independently authoritative journals would create the very reconciliation problem atomic commits are intended to solve. These are proposed designs, not upstream features or accepted repository decisions.

A bounded spike should pass these gates before an adoption ADR:

1. **Runtime:** exact 1.1.0 dependency lock; execute the selected storage adapter under the intended Bun/Node deployment and both current model providers. No model fallback; preserve installed skill text and hashes.
2. **Workflow parity:** fixtures prove Readiness refusal has no Claim, Ready produces one immutable brief, each of at most three cycles starts a fresh Implementer, Verify runs independently, both Reviews gate handoff, and no agent merges.
3. **Crash safety:** kill before/after tool intent, local commit, Verify, push, draft PR, handoff and Escalation. On reopen/status no old model request, shell command or publishing operation runs; uncertain state is classified; exactly one Escalation comment results. Repeated inspection converges.
4. **Ownership and limits:** deadline/interrupt stops every owned child and subprocess; waits cancelling alone do not count as stopped; retry/compaction cannot exceed the Run budget. No background work survives a terminal Run.
5. **Confinement:** reproduce the existing [live confinement probes](../conventions/package-verify.md#5-confinement-pin-smoke), including local commits, and probe absolute paths, traversal/symlinks, inherited credentials, network escape, and every enabled file tool. Assessor/Reviewers remain read-only.
6. **Storage and observation:** reject a second process opening a writable store; simultaneous status is safe; injected append/commit failure leaves inspectable evidence; the chosen durability level preserves required facts. Maintain the existing `events.jsonl`/status contract without starting the scheduler during reads.
7. **Benefit:** compare adapter complexity, retained-memory growth, output/transcript fidelity and latency against the current runner on the same fixtures and one proof Run. Continue only if this removes enough maintained machinery to justify experimental API and Chord dependencies.

Passing the spike would support adopting Durable behind the runtime seam. Automatic recovery, replacing the authoritative journal, changing the host runtime, or changing confinement would each need their concrete policy/architecture decision recorded before migration. This research does not amend accepted ADRs or repair the broader historical documentation drift tracked by [#53](https://github.com/juranki/afk-kit/issues/53).
